Formatting normalized by Prettier. The Phase 2 contextual enquiry test now selects Contact us; sorting responses are matched to the selected sort to prevent an earlier response satisfying the assertion.
3. **Routes:** `/register`; real `/login`; protected `/account`, `/account/profile`, `/account/bookings`, `/account/bookings/:id`, `/tours/:slug/book`.
4. **AuthContext:** exposes user, token, isAuthenticated, loading, error, login, register, logout and refreshUser. Startup and successful authentication load `/api/auth/me`. Temporary profile failures offer retry; responses from an older token cannot restore a logged-out session.
5. **JWT approach:** only the issued access token is stored in sessionStorage. Profile is memory-only. No password, hash, signing secret or database credentials are stored in the frontend. No token decoding is used to authorize actions. Password controls are cleared after requests. This is a documented student-project V1 approach; JavaScript-readable storage does not offer HttpOnly-cookie isolation. Session renewal requires login.
6. **Login:** labelled email/password, show/hide, pending state, friendly invalid-credential/server/rate-limit messages. Returns to a safe intended account or booking route.
7. **Registration:** actual fullName/email/password/optional phone/country DTO. Confirmation stays frontend-only; role is never submitted. Password rule matches the backend: at least 8 characters, a Unicode letter and decimal digit, at most 72 UTF-8 bytes, no null character. Backend always creates Customer. Successful registration signs the customer in using the issued token.
8. **Protected routes:** initialization spinner, retry on profile outage, clean login redirect with local return path. Public browsing remains accessible.
9. **Customer account:** personal welcome and Profile/My bookings/Explore tours links with existing travel imagery. No invented statistics or administrative UI.
10. **Profile:** read-only full name, email, phone and country from `/api/auth/me`. No update endpoint exists; no update operation invented.
11. **Booking creation:** tour summary, future UTC date, phone, optional country, adults 1–1000, children 0–1000, optional requests up to 3000 characters. Backend supplies customer identity and status; no userId, total or status is posted. Confirmation clearly says pending review with final pricing/availability to be agreed. Separate contextual contact/enquiry CTA retained.
12. **My bookings:** actual customer-only array endpoint, photographic list, dates, travellers and distinct status labels. Tour titles resolve through public tour-by-ID lookup; unavailable tours get a neutral fallback. Empty state links to tours. The backend customer endpoint does not paginate, so no unsupported pagination parameters are sent.
13. **Booking details:** uses only `/api/bookings/my/{id}`; handles 403/404 without revealing another customer’s data. Shows status, dates, contact details, travellers and requests. Null total is “To be agreed.” If a server total exists, no guessed currency is attached because the booking DTO provides none.
14. **Reviews:** Customer-only form, keyboard-accessible 1–5 select and required 3–3000-character comment. Posts tourPackageId/rating/comment only. Success says awaiting approval and never inserts the unapproved review into public reviews. Current backend permits customers to review an active tour without requiring a completed booking.
15. **Navbar:** logged-out Login/Plan your trip; authenticated My account/Logout; matching mobile actions; initialization status; no admin links.
16. **401/403:** Axios attaches the current Bearer token. A 401 clears only the matching session, then protected routes redirect. Authentication requests do not attach an old token. A 403 preserves the session and shows an access message. No interceptor redirect loop.
17. **Responsive/mobile:** login, registration, account, profile, bookings, detail, booking form and tour review checked at 360, 768 and 1440 px for horizontal overflow. Mobile account menu/logout tested. Desktop/mobile account screenshots visually reviewed; existing public responsive checks retained.
18. **Backend endpoints:** POST `/api/auth/register`, POST `/api/auth/login`, GET `/api/auth/me`; POST `/api/bookings`, GET `/api/bookings/my`, GET `/api/bookings/my/{id}`; GET `/api/tourpackages/slug/{slug}`, GET `/api/tourpackages/{id}`; POST `/api/reviews`. Existing public endpoints and approved-review reading remain intact. Public `/api/reviews/package/{id}` also verifies new reviews remain unpublished.
19. **Build:** `npm install` completed. Production build and lint pass. Final test totals recorded below when verification finishes.
20. **Customer flow:** real backend registration → logout → invalid-password check → login from tour booking redirect → validated pending booking → My bookings → details → reload restoration → review pending approval → logout → protected-route redirect passed. A second real customer received 404 when requesting the first customer’s booking. Public approved reviews excluded the new unapproved review. Browser storage contained only the access-token key, with no localStorage data.
21. **Problems/contract limits:** no backend modification needed. Read-only profile, unpaginated booking history, no booking currency and no refresh token reflect actual backend capabilities. Customer total pricing/payment remains unimplemented. Automated real writes are opt-in and tracked for exact cleanup. No Git commit or push made for this implementation.
